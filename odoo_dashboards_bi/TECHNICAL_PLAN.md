# Odoo Native BI technical plan

## Product slice

Build `odoo_dashboards_bi` as an Odoo 16 addon in `od-demo-addons`. The AI chat page inside `od_homescreen` and a global systray drawer share the same conversations. Installing BI makes it the provider of the Home AI page. Users attach context explicitly from saved Odoo records, selected rows, list domains, pivot/graph definitions, dashboard widgets or computed dashboard insights. The chat returns sourced prose, numbers, tables and charts. BI is read-only for business data. Odoo owns the user's identity, companies, permissions and data execution. Querygen owns the business map, compiler and OpenAI reasoning. Odoo and Querygen communicate directly, with Odoo initiating calls.

## Direct runtime contract

Browser calls logged-in Odoo RPC for `create_thread`, `start_turn`, `get_thread`, `events_after` and `cancel_turn`. Start commits a unique client request ID per owner and thread. One active turn per thread, stable sequence numbers for events, and idempotent completion prevent duplicate messages or credit entries. A resumable Odoo worker claims pending work, persists each transition, emits owner-scoped bus progress and can replay from Odoo after a reload. Reclaim expired worker leases without duplicating committed tool execution. Old requests cannot overwrite newer state. Recheck live user activity, company membership, AI entitlement and feature state before tool reads and before returning persisted evidence to the model. Include a bounded previous-turn context with the new question, independently of the current checkpoint.

`POST /native-bi/v1/step` is a Querygen server-to-server endpoint using the existing tenant-scoped SaaS credential. Request fields are `run_id`, `step`, `question`, `history`, `context`, `state`, `tool_results`, and server-built `catalog`. `question` and `history` begin a turn. A continuation carries opaque graph state and results identified by the pending tool call IDs. Responses carry `status` (`tools`, `done`, `refused`), `state`, `tools` (`id`, `name`, `arguments`), `card`, and `usage`. The graph plans or narrates one step at a time. Odoo validates each tool against a fixed dispatch table and caps request sizes, rounds, rows, elapsed time and history. Use the pinned published release for that turn. Odoo stores resumable state and the authoritative chat. Querygen holds customer chat and tool results in memory while serving a request. The native subsystem has no Redis, portal, browser-held service secret, or mobile-token dependency. Protect protocol version, tenant, run identity, step number and call-ID matching. Show retryable failures and preserve the last committed step. A model call interrupted before its result is committed may need to run again and may incur provider cost.

## Evidence and authorization

1. Choose a published, caller-visible ontology metric when one answers the question. Query through `run_query` as the actual Odoo user and selected authorized companies. Pin the release, enforce ACLs, field groups and record rules, and reuse lookup, period and decomposition semantics. Never treat a permission failure as a reason to change data paths.
2. If there is a genuine coverage gap, query permitted Odoo models with bounded ORM `search_read`, `search_count` and `read_group`, or the existing bounded exploration compiler with model and join guards. Expose a narrowed catalog, safe typed filters, and explicit fields. No direct database credentials, generic method execution, arbitrary SQL supplied by a user or model, or write tool. Reuse current screen constraints by combining domains rather than replacing the attached domain. Mark this evidence exploratory.
3. Resolve widgets and insights through Odoo's existing dashboard/menu visibility and per-widget checks, with the exact authorized selection, date range and effective filters. A user who can view a result can ask about that result. Treat dashboard results as labeled dashboard evidence, even when its curated aggregate has a broader scope than ORM drilldown. The attached widget is not permission to query a dashboard dataset generically. Deeper reads use the caller's Odoo scope. Never treat insight prose as proof of a value. Preserve its underlying findings, widget IDs and window. Revalidate visibility before replaying a source in a subsequent turn, including after permission changes.
4. Normalize successful tool outputs to evidence with `id`, `source_kind`, `source_id`, definition/release, filters, company scope, `read_at`, columns, rows, units, periods and truncation. Keep evidence attached to the turn that produced it. Generate the chart and table from the same rows. Render numeric claims from evidence references, for example a named column and row key in a given result. Check that the number belongs to the asserted metric, period, dimension and unit before presenting it. When evidence is missing, ask for clarification or report the gap. No invented numbers or totals from a truncated sample.

External data is a planned extension of the existing source and evidence contract. Source IDs are namespace-qualified and persisted separately from ontology metric IDs. The initial source is Odoo. Reserve a registry for source capabilities such as catalog, lookup and query. A future connector must supply its own server-side identity and scope enforcement, with tenant-isolated credentials and declared cross-source join rules. It must produce the same typed evidence and provenance. No connector configuration or runtime dependency is needed for the initial release.

## Native onboarding and settings

Expose Settings → BI → Ontology to authorized stewards. Step through source/module discovery, metadata and bounded profiling, draft suggestions, review and validation, then publish. Querygen reuses existing Builder proposal schemas, canonical packs, and release store. Use OpenAI Responses only. Default `gpt-6.2-sol` for mapping and ontology onboarding, with `gpt-6.1-terra` available as an explicit config choice, and `gpt-6-luna` for answering. Keep model configuration server-side and reusable across tenants. Send metadata and permitted deterministic profile summaries for proposal generation. Validate each proposed metric against the tenant schema before review and reconcile reusable templates before assigning Certified trust. A steward approves and provisions a candidate through the existing Odoo executor, then activates the matching Querygen release. Partial provisioning is visible and cannot become the active release. Surface retry and rollback to the prior release. Support scoped exploratory questions when a published metric is unavailable.

The Settings view shows active release and provisioning status, searchable objects, metrics, dimensions, formulas, units, lineage, source bindings, trust and drift. Use existing ordinary Odoo list/form views where practical. Keep the authoritative graph and editable proposals in Querygen. Odoo stores the operational projection and the deployed hash. Native settings use the same real permission boundary as provisioning and access checks. Restrict sending Odoo content to OpenAI to the configured AI-enabled scope.

## Implementation and acceptance

- **Querygen** Implement and test the stateless LangGraph step from the existing BI code. Add authenticated native Builder/review/activate entry points using existing common functions. Use model roles and structured OpenAI inputs, typed evidence, guarded numeric references, and stable error responses. Test tenant isolation, mismatching continuation IDs, ambiguous metric requests, refusal and follow-ups with a scripted model.
- **Odoo services** Integrate reusable query/explore/provision services, shared thread models and dashboard evidence. Implement the transport, async worker, event replay, ACLs and settings/onboarding actions, then prove user and company parity against scoped Odoo reads. Exercise retry, cancellation and concurrent submission without a model credential.
- **Odoo UI** Implement one OWL conversation component with Home and drawer entry points, context capture, answer evidence, charts and tables, and the native onboarding/settings flow. Prove both Home asset orders, new and resumed conversations, current list/form/pivot context, dashboard widget filters, and bounded native RPCs.
- **Integrated gate** Install together with Home and SaaS on Odoo 16. A steward builds and publishes the map with the selected mapper. Ask a certified metric and follow-up, a custom-field exploratory question, a complex explanation, and a filtered dashboard-widget question. A second restricted user gets the scoped result. Replay and restart a turn without Redis. Exercise invalid or revoked references, withdrawn company membership, and changing a release mid-run. Run focused Querygen and Odoo suites, representative question-bank cases against independent expected numbers, and OWL assets/browser checks. Live provider results require working OpenAI credentials. Ship branches together without altering the existing product's routes or enabling the new integration on unrelated installations.

Reference for model IDs and API capabilities: [OpenAI model catalog](https://developers.openai.com/api/docs/models).

## Verification snapshot

- Native Querygen and reused BI, ontology, compiler and store suites passed together against local PostgreSQL. The standalone native API ran without a Redis process and completed an authenticated two-step turn against Odoo with a scripted model.
- Odoo 16 installed Home, SaaS and Native BI together. Focused Odoo tests covered worker state, ID and ownership checks, typed tool calls, evidence replay after scope changes, related model record rules and widget context. The Odoo JavaScript, CSS and XML asset bundles compiled.
- Minimal synthetic Responses requests succeeded with Sol and Luna. Tenant-specific ontology proposal quality, a full live model-backed onboarding and analytics session, and visual browser behavior still need a pilot pass.
